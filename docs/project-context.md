# mojo-net — Project Context

**Last updated:** 2026-04-25
**Current phase:** spec-quic-pacer-bypass-implementing (`mojo-net-python-bindings` Plan A also ready; existing milestones still implementing in parallel)

## Why this exists

Pure-Mojo networking stack. The death-star deliverables are:
1. A fast HTTP/3 server
2. A feature-complete unified HTTP client (works over H1/H2/H3 with one API)

Single native dependency: rustls via a thin C FFI shim (`librustls-mojo`).

## Scope

- **Wire formats:** QUIC, HTTP/3, HTTP/2, HTTP/1.1
- **Servers:** H3 (primary goal), H2, H1
- **Clients:** Unified client with protocol selection via ALPN
- **TLS:** via librustls-mojo (rustls 0.23)
- **I/O:** sans-I/O at every protocol layer; `boucle` (separate library) used only in examples
- **Conformance:** test-vector + oracle cross-validation methodology (HC-1..HC-5, QC-1..QC-2)

## Non-goals

- Server push (deprecated in H2, dead in practice in H3)
- macOS/Windows I/O backends in v1 (Linux only via boucle)
- HTTP/0.9, SPDY, gQUIC (exception: HTTP/0.9 test infrastructure in `interop/` for QUIC Interop Runner participation)
- Connection migration in v1 of M3 (deferred enhancement)
- WebSocket support in v1 (revisit after M6)

## Key architectural decisions

- **Sans-I/O at every protocol layer.** Application code composes the protocol layer with an I/O loop (boucle in examples). No I/O imports inside `src/`. Exception: `boucle.stackful` (CoroHandle, CoroYielder) is allowed in `src/` because it is a control-flow mechanism with no I/O dependency. Only boucle's I/O primitives (`boucle.net.*`, `CompletionLoop`, `CompletionHandler`) are restricted to examples.
- **Strict-by-default parsing** with opt-in leniency via per-rule flags (24 flags in HTTP/1.1 ParserStrictness).
- **Conformance-driven development.** Each milestone has its own conformance suite with test vectors and oracle cross-validation before production code is written.
- **Test oracles:** h11 + httptools (HTTP/1.1), hyperframe (H2 frames), Python `hpack` (HPACK), hyper-h2 (HC-4 future), aioquic + quiche (H3/QUIC future).
- **Vector format:** JSON, consistent across all protocols.
- **Conformance vs production split:** `conformance/lib/` holds reference implementations used as test oracles; `src/` holds production code that is cross-validated against them.
- **librustls-mojo Wave model:** Wave 1 = TCP-TLS + AEAD primitives (done); Wave 2 = QUIC handshake lifecycle (spec written 2026-04-13, pending planning).
- **Wave 2 FFI convention:** All 15 Wave 2 functions return 0/-1 status with handles in `*out_handle` output params (differs from Wave 1's `rlsm_initial_keys` which returns the handle directly).
- **Wave 2 key transfer pattern:** `write_hs` buffers `KeyChange` in `QuicConnEntry.pending`; `take_keys` materializes it into Wave 1's `KEYS_TABLE`. `Secrets` (for key updates) stored separately in `next_secrets`. `alert_cache` field on `QuicConnEntry` implements clear-on-read alert semantics.
- **QUIC configs are process-lifetime singletons** — no config `_free` functions in Wave 2; callers must not create configs in unbounded loops.
- **QC-1 conformance vectors** (crypto + packet structure, ~35–45 vectors + aioquic oracle scripts) are a separate milestone between Wave 2 and M3 — mirrors HC-4 pattern.
- **M3 split into three sub-milestones:** M3a (codec ~1500-2200 LoC), M3b (connection core ~2200 LoC), M3c (data path ~2000 LoC). Each independently testable. Specs written sequentially (M3a first, M3b informed by M3a's actual types).
- **M3 builds both client + server simultaneously.** Connection state machine is 90% shared; only handshake initiation and HANDSHAKE_DONE direction differ. Enables loopback testing without external tools.
- **Hybrid state machine design:** Bitflags for Connection state (~22 orthogonal flags, TQUIC pattern), explicit enums for Stream state (6-8 sequential states per side, quinn pattern). Different complexity profiles warrant different approaches.
- **PTO in M3b, not M4.** Required for handshake correctness — without PTO, lost CRYPTO frames are never retransmitted and the 3x anti-amplification limit deadlocks the connection.
- **Full RESET_STREAM + STOP_SENDING in M3c.** quic-go v0.49.0 proved that retrofitting stream lifecycle onto stubs causes stalls, deadlocks, and memory leaks.
- **Dummy congestion controller for M3.** Tracks bytes_in_flight and time_sent (data M4 needs) but never reduces cwnd. Real CC (CUBIC/BBR) in M4.
- **Static flow control windows for M3:** 10 MiB connection, 1 MiB stream, 50% update threshold. Auto-tuning deferred to M4.
- **Security SHOULD/MAY = MUST.** PN skipping, ACK validation, amplification limits, PATH_RESPONSE caps — all mandatory. CVE analysis (50 CVEs across 14 stacks) showed 84% are remotely exploitable and most exploit optional security measures.
- **Basic stateless Retry in M3b.** Primary amplification defense. AEAD-encrypted tokens with server secret. NEW_TOKEN deferred to M4.
- **Test oracle strategy:** aioquic primary (pure Python, already integrated) + quiche as compliance reference (96-100% formal verification). Loopback tests (client↔server) need no oracle.
- **HTTP/3 is the canonical shape.** API design leads with H3 semantics; H2 and H1 are graceful projections of that shape onto older wire formats. Build order is H2 first (HC-4 → M5.5) for validation reasons, but the public API is designed against H3 semantics from M2.5 onwards.
- **H3CoroServer wraps QuicConnection directly** (same as H3HandlerServer), not H3Connection. Consistent constructor surface; hides QUIC details from callers. Trailer detection is implicit: second `HEADERS_RECEIVED` on same stream_id = trailers (trusted to H3Connection to prevent a third).
- **Handler execution model is callback-based** (γ hybrid: per-stream queue with `try_read` / `on_body_available`). Sync and async adapters deferred — Mojo's coroutine runtime is experimental and not pluggable to custom I/O sources today (verified via Modular docs + GitHub issues 2026-04-07).
- **Body ownership across handler callbacks: hybrid with explicit `detach()`.** Default is borrowed from runtime; handlers call `body.detach() -> DetachedBody` to take ownership for forwarding (reverse proxy) or wrapping (SSE). One-way; no resurrection.
- **Capability negotiation: runtime flags + standalone `H3StreamExtension` trait.** Not type-state generics (would create origin propagation through M6). Not trait inheritance with method override (fictional in Mojo). Standalone H3 trait avoids both pitfalls.
- **Session trait is compile-time monomorphic.** M6's connection pool composes via tagged enum or vtable indirection — decision deferred to M6 implementation time. The trait surface itself does not commit.
- **Client request ownership: owning, not borrowing.** `Session.submit(var req: Request)` consumes the request; `RequestHandle` owns derived state; no origin parameters propagating through `List[RequestHandle]`.
- **Default constants match hyper exactly.** 1 MiB stream window, 16 KiB max frame, 200 max concurrent streams, 20s keepalive. Subject to change after benchmarking; not stable API.
- **Mojo 0.26.2 conventions used in spec/code:** `def` for trait methods and ordinary methods; `fn __del__(deinit self)` for destructors; `def __init__(out self, *, deinit take: Self)` for move constructors; `comptime` constants instead of `@parameter`; integer constants for ALPN identifiers (no per-stream `String`).
- **M5 split into M5a + M5b.** M5a = H3 frame codec + QPACK static-only + Huffman + QC-2 conformance vectors (~1400–1800 LoC). M5b = H3 connection state machine + H3HandlerServer + H3Session + GOAWAY (~1300–1700 LoC). Mirrors M3a/M3b rhythm. M5b spec written after M5a is implemented (same pattern as M3a→M3b — M5b's types are informed by M5a's actual code).
- **QPACK static-only for M5.** Set `SETTINGS_QPACK_MAX_TABLE_CAPACITY = 0`. Create encoder/decoder QPACK streams per RFC requirement but keep them idle. Dynamic table deferred to M6. Huffman encoding included in M5a (pure codec function, no state).
- **QC-2 vectors folded into M5a** (not a standalone milestone). H3 frame + QPACK static vectors cross-validated against aioquic. Same oracle pattern as QC-1 (oracle script generates JSON; Mojo cross-validation reads and compares).
- **STREAMS_BLOCKED (RFC 9000 §4.6) as a micro-prereq before M5a.** ~180 LoC in connection.mojo + stream_map.mojo. Same dedup pattern as M4b's DATA_BLOCKED. Closes M4b required-later item.
- **M4 split into M4a + M4b.** M4a = CUBIC + pacer + persistent congestion + send gating. M4b = HyStart++ + delivery-rate + minmax + ECN + BLOCKED emission + PN skipping + FC auto-tuning. Same rhythm as M3's three-sub-milestone split. Decision driven by third-round reviewer scope concern: combined M4 exceeded the M3c ~2590 LoC single-plan ceiling.
- **CC pluggability via tagged-variant struct.** `CcController` combines QuicEvent's flat-tag pattern (`kind: UInt8` discriminant) with the nested-Copyable-struct pattern used elsewhere in M3 (e.g. `PacketNumberSpace` holding `EncryptionLevel`). Reserved `kind` values for future BBR/BBRv3. Variants declared `Copyable, Movable`; unused variant state wastes ~500 bytes per connection (negligible).
- **TQUIC is the primary QUIC reference implementation**, with quinn consulted on security-critical gaps where TQUIC is behind (notably PN skipping for CVE-2025-4820 optimistic-ACK defense — deferred to M4b but confirmed as MUST per security-posture decision line 51).
- **M6 two-layer client architecture.** `HttpClient` (sans-I/O) owns pool + dispatch + redirect/retry logic, testable with MockSession. `HttpCoroClient` wraps it with boucle.stackful for the user-facing ergonomic API. Matches the Server-side pattern (HandlerServer + CoroServer).
- **Session composition via tagged enum.** `SessionSlot` has `kind: UInt8` discriminant + `Optional[H1Session]` / `Optional[H2Session]` / `Optional[H3Session]`. Same pattern as `CcController` (M4a). Decision resolves the "tagged enum vs vtable" question deferred since M2.5a.
- **H3 never attempted speculatively.** UDP+QUIC path only when Alt-Svc explicitly advertises "h3". Default connections use TCP+TLS with H2/H1 ALPN negotiation.
- **Content-Encoding decoding via Rust FFI** (flate2 + brotli crates in librustls-mojo). Stateful streaming decoder (init/feed/finish lifecycle) to handle chunked responses incrementally.

## Open follow-ups (post-M2.5a)

- **M3c: SendBuf.on_ack ignores bare FIN-only frames** — ✅ fixed in M4c (`1a2de12`). Bare-FIN guard added inside `ack_len==0` branch.
- **M3c: BLOCKED frame emission** — ✅ implemented in M4b. `DATA_BLOCKED` + `STREAM_DATA_BLOCKED` emitted on FC exhaustion with `blocked_at` dedup guard.
- **M3c: Integration test coverage gaps.** Severity: required-later. Trigger: before M4 relies on behaviors that aren't tested end-to-end — specifically FC limit-violation error paths (FLOW_CONTROL_ERROR, FINAL_SIZE_ERROR), MAX_STREAM_DATA/MAX_DATA flow cycle, linear MAX_STREAMS growth via wire, CID retire→reissue exchange, and loss+retransmit of M3c frame types (RESET_STREAM, STOP_SENDING, MAX_*, NEW_CID).
- **M3c: Pre-commit mutation vs packet-build failure.** Severity: optional. Trigger: AEAD encryption failure post-handshake. `_build_frames_for_space` drains state (retire queue, mark_advertised, needs_* flags) before `_build_packet` runs — if AEAD raises, that state is lost and loss detection can't recover.
- **M3c: Spurious STREAM_READABLE events.** Severity: optional. Trigger: performance profiling. Each STREAM frame that touches the readable region fires STREAM_READABLE even if the app hasn't consumed anything yet.
- **M5b: H3HandlerServer._on_request swallows handler exceptions.** Severity: required-later. Trigger: when H3HandlerServer needs to respond with 4xx/5xx on handler error. If the handler raises in `on_request`, the stream context is not heap-allocated and not inserted into `_streams` (current behavior after fix), so the request silently drops. Same pattern as H2HandlerServer — should be addressed when proper error response dispatch is added.
- **M3c: app_frames_sent not cleaned on connection close.** Severity: optional. Trigger: memory growth under rapid connection churn. Entries for packets neither ACKed nor detected-lost linger until the connection is freed.
- **HC-4 design pass.** The HC-4a/4b/4c split was sketched before M2.5a's trait surface was concrete. Worth re-walking the spec against the now-shipped types — particularly `StreamHandler.on_request` taking `var body` (cross-callback streaming bodies need either `body.try_detach()` on a `mut` ref or splitting into `on_request_headers` + `on_request_body`), `Session.run_until` taking `Deque[UInt64]`, and `RequestBody` having no trailer slot.
